# mirx

`mirx` is a Windows-only native Win32 Matrix client in Rust. The current prototype includes the typed `mirx-core` facade, the Win32 UI shell, Nix-backed Linux-to-Windows GNU cross-build tooling, Wine smoke coverage, and a DLL import gate for the release artifact.

## Status

- Vertical-slice prototype scaffold is in place.
- `mirx-core` owns the Matrix SDK runtime boundary and has offline tests plus env-gated live Matrix coverage.
- Matrix SDK timeline, state, and send-queue inputs enter `mirx-core`, which normalizes them into typed room activity/state events that Win32 stores and renders.
- Reactions, media, read-state, typing, threads, and verification slices extend that typed boundary instead of adding separate UI-only paths.
- `mirx-ui` is a native Win32 shell with deterministic Wine automation, focused snapshot coverage, and a live login/session-restore/sync/rooms/send slice through `mirx-core`.
- CI builds the shipped exe and its release zip on every push, and publishes the zip on a `v*` tag (see CI and Releases).

## Local Commands

The devshell provisions local `.rustup` and `.cargo-home` caches, installs the stable Rust toolchain with `clippy` and `rustfmt`, enables the `x86_64-pc-windows-gnu` target, and exports the MinGW pthread include/lib settings validated by the spike. There are two: `nix develop .#build` builds, lints, tests and packages, without Wine, and everything in it comes from cache.nixos.org; the default `nix develop` adds the patched Wine (built from source, see `flake.nix`), Xvfb, xdpyinfo and ImageMagick for the Wine lanes. Run either from the repo root.

```sh
nix develop -c ./scripts/lint.sh
nix develop -c cargo test --workspace
nix develop -c ./scripts/cross-build.sh
nix develop -c ./scripts/package.sh
nix develop -c ./scripts/wine-smoke.sh
nix develop -c ./scripts/windows-ui-tests.sh
nix develop -c ./scripts/ui-snapshot.sh
nix develop -c ./scripts/dll-gate.sh
nix develop -c ./scripts/live-lane.sh
nix develop -c ./scripts/measure.sh
nix develop -c ./scripts/size-audit.sh [--top N] [--base <rev>]
```

The tests drive mirx through its automation harness: a `WM_COPYDATA` and shared-memory protocol that dumps the UI's state and acts on it, the `--automation`, `--render-state <file.json>`, `--frame-size WIDTHxHEIGHT` and `--self-test` launches, and a record of what the UI did. Only the `automation` feature of `mirx-ui` builds it (the bin's unit tests always have it); the shipped exe, which `cross-build.sh` builds, has none, and its only flags are `--auto-close` (start, then close by itself) and `--help`. `windows-ui-tests.sh` and `ui-snapshot.sh` build with the feature, and so must a manual run of the GUI suites (`cargo test --target x86_64-pc-windows-gnu -p mirx-ui --features automation --test automation_driver`), which otherwise are skipped. `live-lane.sh` builds the `release-automation` profile (the release profile with the feature, in `target/<triple>/release-automation/`), so it never replaces the shipped exe. `wine-smoke.sh` starts the shipped exe with `--auto-close` and checks it refuses `--automation` with a usage that names no harness flag.

`lint.sh` runs the static checks: `cargo fmt --check`, the clippy lanes (the host workspace; on the Windows target `mirx-ui` without and with `automation`, and `mirx-testkit`), `actionlint` over the workflows and `shellcheck` over the scripts kept clean (`cross-build.sh`, `dll-gate.sh`, `lint.sh`, `package.sh`, `trademark-scan.sh`).

`cross-build.sh` builds the shipped exe, `target/x86_64-pc-windows-gnu/release/mirx-ui.exe`, and is the only place that says how (`dll-gate.sh` and `wine-smoke.sh` call it when given no exe). It remaps the builder's directories (`$CARGO_HOME` to `/cargo`, the repo to `/mirx`) in the source paths panic locations name, so the exe names no home directory and the same commit builds the same bytes anywhere.

`dll-gate.sh` checks the release exe: its DLL imports against an allowlist, that it is a Windows GUI-subsystem program, and that it carries its resources (icon, group icon, version information and the manifest, with the Common-Controls 6 dependency and Windows 10/11 as its supported OS). It also fails if the exe contains "mIRC" in any case (`trademark-scan.sh`: ASCII or UTF-16, strings, resources, panic messages and the source paths they embed; "mirx" is fine): nothing shipped may carry that trademark. It fails if the exe has the automation harness: "automation" in any case, a harness launch flag or the protocol's `protocol_version` field (ASCII or UTF-16), with each place and its text. And it fails if the exe names the repo's or `$CARGO_HOME`'s directory.

`package.sh` builds the release zip people download, `target/package/mirx-<commit>-windows-x64.zip` (`<commit>` is the commit's first 8 hex digits, followed by `-dirty` when tracked files differ from it), and prints its path. It runs `cross-build.sh` and `dll-gate.sh`, and the zip holds one folder of that name with `mirx-ui.exe`, `README.txt` (`packaging/README.txt`, a short guide for users; this README names mIRC and is never shipped), `LICENSE.txt`, `THIRD-PARTY-LICENSES.txt` and `COPYING.MinGW-w64-runtime.txt`. `THIRD-PARTY-LICENSES.txt` is cargo-about's list of the crates linked into the exe, under each licence's text, and says where their source is (crates.io; mirx's repository for its vendored matrix-sdk crates); a crate under a licence that `packaging/about.toml` does not accept fails packaging until someone has read that licence and added it. The MinGW-w64 runtime, linked statically, asks for its notices beside the binary: the devshell takes its notice file from the runtime's source. Every entry carries the commit's time, so the same commit gives the same zip byte for byte, here and in CI. The zip is extracted again and `trademark-scan.sh` reads every file in it and their names; only a zip that passes reaches `target/package/`, alone there.

`size-audit.sh` says where the release exe's bytes go. It builds the release exe unstripped (otherwise the release profile as it is) in `target/size-audit`, never `target/`, writes `target/size-audit/report/<rev>[-dirty].tsv` (bytes and demangled name of every `.text` symbol, sizes measured to the next symbol's address since COFF symbols carry none) and prints the size `strip` leaves of it (close to the shipped exe, which the linker strips and whose source paths `cross-build.sh` shortens), the `.text` and `.rdata` sizes, the biggest symbols and the sums by crate. `--base <rev>` also builds that commit in a temporary worktree with a target dir of its own (`target/size-audit-base`, kept for the next run) and prints the stripped delta, the change by crate and the symbols that grew and shrank most. A first build takes several minutes, a rebuild a few. The crate of a symbol is the first `crate::` path in its name, so a generic counts under whichever crate comes first, and LTO inlines callees into their callers: judge a change by the totals and the crate sums more than by one symbol.

`windows-ui-tests.sh` runs the Wine UI suites in parallel shards (`MIRX_UI_TEST_SHARDS`, default 12), each with its own Wine prefix, Xvfb display and temp dir, and its tests one at a time; `-- [--exact] <filter>...` runs only the tests whose names match, and each shard's output is kept in `target/windows-ui-tests/`. The `scale` suite loads 200 rooms and checks, through the refresh counters in the UI dump (rows built, rows wrapped, treebar and switchbar rebuilds), that one change costs one window's work; `-- two_hundred_rooms` runs it alone. It also starts a thousand rooms, with unread messages and highlights, and checks that every room gets its window and button without the active window changing or the windows losing their height, and that a stream of activity rebuilds neither bar (`-- a_thousand_rooms`).

Normal checks remain offline and deterministic. They do not require network access or Matrix credentials.
Wine/Xvfb automation and screenshot diffs are required local gates for the Win32 shell, but real Windows remains authoritative for DPI, keyboard/input behavior, DPAPI, and installer validation. Checked by hand on real Windows, not by the gates: the layout at 125%, 150% and 200% display scaling, and on a second monitor with another scaling; no console window opens when mirx starts from Explorer; the icon shows in the taskbar, Alt+Tab, Explorer (large icons) and the tray; Task Manager lists "mirx" and Properties > Details shows the version; controls are themed and the switchbar keeps its activity colours; the switchbar's buttons show their icons left of their labels and wrap onto rows without clipping a button, and the treebar's and switchbar's icons are crisp; the toolbar's greyed buttons look disabled and its tooltips show; `mirx-ui --help` from `cmd` shows a box; a panic in an interactive run shows the error box and writes `crash.log` (and whether Windows Error Reporting adds a dialog of its own after it).
`ui-snapshot.sh` captures each case in `tests/ui-states/` after the snapshot driver's actions, and a few of them again as `<case>-dpi144` in a prefix at 144 dpi (150%), at the default frame size; its prefix lets Wine draw window captions and stops the caret blinking. Each PNG is the frame's outer rect from the screen's corner (the case's frame size, else 1024x768, or the 1280x1024 screen at 144 dpi), and a case that draws anything outside it fails instead of being cut. A `collapse:<node>` action folds a treebar item: `space:<room_id>`, or a view (`status`, `room:<room_id>`, `thread:<room_id>|<root_event_id>`). A `dialog:<name>[:<Options page>]` action (for example `dialog:select_server` or `dialog:options:Chat/Messages`) opens a dialog over the window and must be the case's last action. So must a `drag:<line>,<offset>:<line>,<offset>` action, which presses the left button at a byte offset into one visible line of the active timeline and moves to another without releasing it, leaving the mark on screen.

## CI and Releases

`.github/workflows/ci.yml` runs on every push, every pull request and every pushed `v*` tag, in the `build` devshell (no Wine is built):

- `checks`: `lint.sh` and `cargo test --workspace`.
- `package`: `package.sh`, and the zip as a run artifact named after it (`mirx-<commit>-windows-x64.zip`), uploaded as it is (no zip around it) and kept 30 days: the run's Summary page lists it for download, for anyone signed in to GitHub.
- `release`, only for a `v*` tag, once both passed: publishes the tag as a GitHub release with that zip and notes generated from the commits since the last release (`gh release create --verify-tag --generate-notes`). It is the only job that may write to the repository. Nothing is released otherwise.

Both build jobs cache `.rustup`, cargo's registry and `target/` (keyed on `rust-toolchain.toml`, `flake.lock` and `Cargo.lock`), and a newer push to a branch cancels its older run. Actions are pinned by commit. To publish a release, push a tag: `git tag v0.1.0 && git push github v0.1.0`; the repository's Settings > Actions > General must let workflows run (the release job asks for `contents: write` itself).

`.github/workflows/wine.yml` runs only by hand (Actions > wine > Run workflow): `cross-build.sh`, `wine-smoke.sh`, `windows-ui-tests.sh` (4 shards) and `ui-snapshot.sh` in the default devshell, keeping the Nix store between runs with `nix-community/cache-nix-action`, since the patched Wine is not in cache.nixos.org and its first build takes an hour or more on a hosted runner; the UI suites' logs are kept when it fails. Its runtime on a 4-core hosted runner is untried. The Wine lanes stay required local gates, and the live lane stays local: hosted runners can open KVM, but each run would also build the VM's system and Wine, and it is the slowest lane and the one most worth running on a real machine.

## Windows Integration

mirx is a Windows GUI program: started from Explorer or a shortcut, no console window opens beside it. Run from `cmd` without a redirection it has no console output either, so `--help`, a usage error and a startup error show in a message box; with a redirection (or from a script or the test harness, which pass their own handles) they go to stdout and stderr as usual, and the exit code is always set. The exe carries its own icon, version information (Task Manager lists it as "mirx") and a manifest: Windows 10 and 11, no elevation, and the themed (Common Controls 6) look for buttons, edits, lists and the status bar. mirx is system-DPI-aware: at any display scaling its text is sharp, and every bar, list, dialog and image is laid out at the system's scaling, the window opening at 1024x768 scaled (but never larger than the screen). Moved to a monitor whose scaling differs from the main one's, it is stretched by Windows until per-monitor scaling lands. Fixedsys, the default text font, is a bitmap font with few sizes, so at 150% or more its text stays small: `/font` to a TrueType face (Courier New, Consolas) for larger text. If mirx crashes, it appends a report (version, time, thread, message, place and a backtrace) to `%LOCALAPPDATA%\mirx\ui-shell\crash.log`, says so in an error box, and ends.

## Live Matrix Checks

`live-lane.sh` runs the live lane: a release `mirx-ui.exe` with the automation harness (the `release-automation` profile), driven through its GUI under Wine by the `live` suite (`crates/mirx-ui/tests/live.rs`), against a real Conduit homeserver, all inside a NixOS VM (`nix/live-lane.nix`). matrix-sdk clients in the test process play the other users, and every test registers users of its own. The tests: messages both ways in a room joined by its address and in an encrypted room; Log Out, which ends the device on the server, and signing in again as a new device; recovery, which brings an encrypted room's history back after Log Out and a new sign-in; a session signed out from another device; a restart that restores the session and catches up on what was said meanwhile; a restart with connect on startup off, which shows the room and its nick list before connecting; a restart and a Disconnect/Connect on a quiet account, which connect within seconds and say each thing once in Status; ignore-list changes made in a row, typed and from the Address Book, which all reach the server; two direct-room invitations accepted back to back, which both stay direct rooms; and rank changes typed in a row and several nicks in one `/op`, which all reach the server's power levels; and Room Settings, whose one OK renames the room, sets its topic, moderates it, makes it invite only and lifts a ban, each of which a peer reads from the server, while the room's window says `* Alice turns moderation on`; and the Sessions dialog, which renames another session of the account and signs it out, as the server then lists it; and Perform on connect, whose first connect joins a room by its alias and messages it, and whose reconnect messages it again; and an alias `/greet /query $$1 | say hi $1` typed in a shared room, which greets the peer in the direct room it makes, never in the shared room; and an invite to a room and one to a direct room, whose lines name the inviter, with `Join rooms when invited` joining the room behind Status and leaving the direct room's invite alone; and exiting with a room's window active, which moves the room's read marker to its last line, as another session of the account reads from the server and the next start shows; and Log Out with Conduit stopped (the lane's VM has a switch that stops and starts it), whose dialog removes the session from this computer only, while the server, started again, still lists the device. The script builds the Windows binaries with the dev shell's toolchain, adds them to the Nix store, and builds the VM test, which runs the tests every time; `-- <filter>...` picks tests by name. The VM test is built by the Nix daemon, which needs the `kvm` and `nixos-test` system features. A run takes 5 minutes or more once the VM's system is built (the first build takes much longer): 2 to 3 minutes in the VM (booting it and a Wine prefix, then about a minute of tests), the rest staging the binaries and waiting for the Nix daemon, which queues the build when it is busy. What Conduit lacks (refresh tokens, soft logout, OAuth) stays covered by the mock homeserver tests.

`mirx-core` also has live Matrix checks of its own, opt-in through:

- `MIRX_HS`
- `MIRX_USER`
- `MIRX_PASS`
- optional `MIRX_ROOM`

Missing or empty `MIRX_HS`, `MIRX_USER`, or `MIRX_PASS` makes them return early without network access.

```sh
MIRX_HS=... MIRX_USER=... MIRX_PASS=... MIRX_ROOM=... \
  nix develop -c cargo test -p mirx-core --test live_matrix
```

`MIRX_ROOM` is optional for the login, restore, sync, and logout coverage. It is required for send coverage and for the fully-read marker verification. `MIRX_ROOM` must be a room the account has already joined; the test creates the event-backed message itself before issuing `MarkRoomRead`.

The UI session file still lives at `%LOCALAPPDATA%\mirx\ui-shell\session.json`, but its payload is now DPAPI-protected binary data rather than cleartext JSON. The Matrix SDK SQLite store passphrase is generated per profile and persisted separately in `%LOCALAPPDATA%\mirx\ui-shell\store-passphrase.dpapi`, and refreshed Matrix access/refresh tokens are written back through the same protected session store. A browser sign-in's OAuth 2.0 tokens and client ID are saved the same way, and its refreshed tokens are saved again as the server rotates them. The password is never persisted.

The menubar follows mIRC: `File` (Connect, Disconnect, Select Server... (`Alt+E`), Log Out, Exit), `View` (Toolbar, Switchbar, Treebar), `Tools` (E2EE recovery, Reset E2EE Identity, Export and Import Room Keys, Verify This Session, Sessions..., answering a verification, Address Book... (`Alt+B`), Colors... (`Alt+K`), Options... (`Alt+O`), Aliases... (`Alt+A`)), `Commands` (prompts for a slash command's argument and runs it), `Window` (Cascade, Tile, Arrange Icons) and `Help` (Help Topics, About mirx). Room, message and nick-list actions are on their right-click menus.

Under the menubar is mIRC's toolbar. Its buttons are Connect (Disconnect instead, whenever `File > Disconnect` applies: syncing, signing in or waiting to retry), Options, List Rooms, Join Room, Address Book, Colors and Send File; then Cascade, Tile Horizontal, Tile Vertical and Arrange Icons; then Help. Each does what its menu item or command does and names itself in a tooltip. A button is greyed when its menu item is.

The switchbar has one fixed-width button per window, 120 pixels by default, and wraps them onto as many rows as the frame's width needs, like mIRC's switchbar with Lines set to Auto; the MDI area shrinks to fit, but always keeps at least 100 pixels: with more buttons than that leaves rows for (hundreds of rooms), the last rows are cut off, and their windows are reached from the treebar or `Ctrl+Tab`. Windows that open while another is active (a sync's new rooms) open behind it, so the active window stays as it is. `/toolbar [on|off]`, `/switchbar [on|off]` and `/treebar [on|off]`, or the matching `View` items, toggle or set whether each bar is shown. Without an argument the View menu toggles and the command echoes the current state. Drag the band between the treebar and the windows to resize the treebar. Its width, 40 to 800 pixels at 100% scaling, is saved, and the windows always keep at least 100 pixels.

Switchbar buttons and treebar items show a window's icon and name: the homeserver for Status, `#` for a room, a person for direct messages, an envelope for an invite, a speech bubble for a thread, the List Rooms page for the Rooms List, and in the treebar a folder for a space (a room removed from a space, whose `m.space.child` is left without `via`, is not under it, as the spec says). The treebar draws its lines, and every item with others under it, Status included, has an expand button. Unread state shows as colour, as in mIRC: maroon for an event, red for a message, blue for a highlight, by default; `Options > Display` changes them. The colours come back after a restart, from the server's unread counts. Activating an unread window tells the server it was read (a read receipt), and so do new lines in the active window while mirx is the application in front and not minimized, both only while connected, so your other clients agree and the window is not unread again after a restart; a room only marked unread elsewhere stays so until its window is activated. Every message the server counts unread has a line, so every unread room can be read: a sticker shows as an image does (`* Bob sent sticker: a waving cat`, with its picture), a poll as `* Bob started a poll: Lunch? 1) Pizza 2) Sushi` and `* Bob ended the poll "Lunch?": <its results>` (votes are not shown, and there is no `/vote`), an in-room verification request as `* Bob wants to verify @carol:example`, and any other message type (a location, a server notice, a type mirx does not know) as `* Bob sent unsupported m.location: <its text>`. A collapsed item takes the strongest colour of the windows under it, stays collapsed as rooms come and go, and opens again when one of its windows is activated, for example from the switchbar. Collapsing a folder never changes the active window.

`Tools > Options...` (`Alt+O`) opens mIRC's Options window, a tree of pages: `Connect > Options` (connect on startup, reconnect and retry, and the `Perform...` button; see Connecting below), `Chat` (mIRC's IRC page, below), `Chat > Messages` (timestamps on or off and their format, with the tokens listed, and `Send typing notifications`, see below), `Chat > Highlight` (highlight words), `Chat > Logging` (see Logging below), `Display` (switchbar button width, 40 to 400 pixels at 100% scaling, and the switchbar's Event, Message and Highlight colours, each picked from the 16-colour palette), `Display > Tray` and `Display > Tips` (see Tray and tips below), and `Other` (the window buffer, see below). OK checks every field: a wrong one shows its page with an error box, and nothing changes until it is fixed; otherwise the settings are saved and take effect at once. Cancel or `Esc` changes nothing. As in mIRC, the tree is labelled `Category:` and the selected item names the page.

`Options > Chat` holds the options of mIRC's IRC page that have a Matrix counterpart. `Show rank prefix` (off by default) puts the sender's rank glyph (`~&@+`, as in the nick list) before the nick of a message line in a group room's window and its threads, `<@Bob> hi`, from the rank the member has now (a line does not keep the rank it was said with); the room's log and tips follow it, and direct messages never show one. `Join rooms when invited` (off) accepts an invite to a group room as it arrives, with its window opening behind the one in front, as mIRC's minimized; invites to direct messages or a space are left to you. `Show in active:` `Away`, `Invites` and `Whois` (all on) say where those lines print: an away user's line in your direct messages window with them, an arriving invite's line and `/whois` answers in the window in front; off, each prints in Status. mIRC's other options of that page (rejoining on kick, hiding pings, the other "Show in active" kinds, and so on) have no Matrix counterpart yet and are not there.

`Tools > Colors...` (`Alt+K`) opens mIRC's Colors window. A preview shows every part of a window: the treebar, a timeline with one sample line per kind of text, the editbox and the nick list. Click a part, or pick it in the drop-down, then click one of the 16 palette colours (or move with the arrow keys) to give it that colour. The items are mIRC's that mirx draws: Background; Action, Highlight, Info, Invite, Join, Kick, Settings (mIRC's Mode), Nick, Normal, Notice, Notify, Other, Own, Part and Topic text; Editbox, Listbox and Treebar and their text; and Gray text (typing, reactions, reply quotes, deleted messages, messages still sending). `Reset` puts back mIRC's default colours; OK saves the scheme and every window takes it at once, Cancel changes nothing. The scheme is saved as palette indices 0 to 15 in `mirx.ini`'s `[colors]` section (`join=3`, `editbox_text=1`, ...). Unlike mIRC, error lines and messages that failed to send stay red whatever the scheme, the 16 palette colours themselves cannot be changed, and there are no named schemes to save and load. Highlight words are kept on the Matrix server, not in `mirx.ini` (see `Options > Chat > Highlight`).

Every dialog opens centred on the mirx window, in the 8-point dialog font. The first field has the focus; `Tab` and `Shift+Tab` move between the fields and buttons, `Enter` presses the default button (OK) and `Esc` cancels.

Notifications follow Matrix push rules, which live on your server and are shared with your other clients. A room's right-click menu in the treebar has `Notifications > All Messages`, `Mentions and Keywords` and `Mute`; the check shows the room's mode, or, if none was set for it, the account's default for rooms of its kind (one-to-one or group, encrypted or not), usually All Messages. Invites have no mode. A muted room's window and buttons only ever turn maroon (something happened), never red or blue, and it never flashes the frame. In a Mentions and Keywords room an ordinary message still turns it red but does not flash, even in direct messages; a mention or keyword turns it blue and flashes as usual. `Chat > Highlight` lists the highlight words: type one or several (`deploy, build, *help*`) and press `Add` or `Enter`, or select one and press `Delete`. A word is matched as a whole word, `*` and `?` are wildcards, and a message containing it highlights (blue) and notifies. Words another client added that only notify, without highlighting, show as `word (notify only)`; adding them again makes them highlight. The page is greyed while not connected. Both the menu and OK send the change to the server: the check and the list update when the server's echo arrives with the next sync, so a change made while disconnected shows only after reconnecting.

The Rooms List is mIRC's channels list for a server's room directory. `/list [-s server] [match text]`, `Commands > List rooms...` or `Alt+L` opens it. Without `-s` it lists the user's own homeserver, and the match text is matched by the server against names, topics and aliases. The rooms arrive page by page, up to the first 1000. The caption shows progress: `Rooms List [matrix.org] "rust" - listing...`, then `- 42 rooms`, or `- 1000 of ~5300 rooms` when the cap is hit. Click a column header (Room, Users, Name, Topic) to sort by it, and click it again to reverse; Users sorts the busiest rooms first. Double-click a row or press `Enter` on it to join the room, or to switch to its window if already joined. A new `/list` replaces the listing, and closing the window drops it.

Every join you ask for opens the room's window and makes it active, as `/join` does in mIRC: `/join`, a Rooms List row, `/query` creating a direct room, accepting an invite and `/create` (but not `Options > Chat`'s `Join rooms when invited`, which joins behind the window in front). An invite opens its window in the treebar, behind the one in front, and prints mIRC's line naming who sent it, `* Bob (@bob:example.org) invites you to join Ops` (`invites you to direct messages` for a direct room), from the profile in the invite; a server that sends no profile of the inviter's with the invite (Conduit) gets `* @bob:example.org invites you to join Ops`. Invites already there when mirx starts or signs in are not announced. Direct rooms are listed in the account's `m.direct`, shared with your other clients; creating or accepting one reads the server's copy and writes it back, one at a time, so direct rooms created or accepted together all stay direct. An entry of it that is not a list of room IDs (old clients wrote some) is ignored, not the whole list, and so is a room tag whose order is no number (the tag stays) and an ignore-list entry that is no user ID; a Room Settings event that does not decode reads as unset. `/create <name>` creates a private, invite-only, encrypted room. `/create -public #alias [name]` creates a public room listed in the room directory under `#alias:<your server>`; the alias must be on your own server, and the name defaults to the alias. The joined window takes the focus, and the window you were in is left, so its line marker moves as on any window change. When the active window's room goes (you part it, reject its invite, or are kicked), the selected room's window becomes active, else the first room's, else Status; a thread window whose thread goes gives way to its room's window.

Commands name rooms as mIRC names channels. A room argument is a room ID (`!abc:example.org`), an alias (`#ops:example.org`, canonical or alternative, case-sensitive), a short alias (`#ops`, matching any alias's localpart) or the room's display name; `/msg`, `/notice`, `/names`, `/part`, `/invite`, `/window` and `/topic` take one, and a name that fits two rooms is refused as ambiguous. A room joined by an alias answers to it at once, before its first sync brings the aliases it publishes. `/topic` shows the active room's topic, `/topic #room` another room's, and `/topic [#room] text` sets it. A refused request about a room, such as a kick or `/op` without the power to, prints in that room's window. `/op <nick> [nick ...]` gives members moderator power (power level 50) and `/deop` takes it back (to the room's default level); `/voice` lets members speak when the room is moderated (the lowest level above the room's default that may send messages) and `/devoice` takes that level back; several members at once as in mIRC (`/op Bob Carol`). It is all or nothing: if one nick is unknown, ambiguous, named twice or would not change (`Bob already has moderator power`, `you cannot remove your own moderator power`), that is printed and nothing is sent; otherwise the room's power levels are written once, and the room shows one line, `* Alice sets power level: Bob 0 -> 50, Carol 0 -> 50`. Each change reads the server's copy of the power levels and writes it back, one at a time per room, so rank changes made in a row all stay; a change another client makes to the same room's power levels at the same moment can still be lost. A power-levels change that turns moderation on or off, or changes who may set the topic, says so: `* Alice turns moderation on`, `* Alice lets only moderators set the topic` (or `lets everyone set the topic`), both joined by `and`, moderation first, with the levels it also changed after it (`* Alice turns moderation off; power level: Dave 1 -> 0`) and `; room permissions changed` when other levels changed too; a join rule change prints `* Alice makes the room invite only`, and the directory listing, which is not room state, prints nothing. `/ignore <nick|@user:server>` adds a user to the account's ignore list (`m.ignored_user_list`, shared with your other clients; the server stops sending their events), `/unignore` removes them and `/ignore` lists it; the `* Added ...` and `* Removed ...` lines print when the server's echo arrives. The Address Book's Control tab edits the same list (see below). Each change reads the server's copy of the list and writes it back, one at a time, so changes made in a row all stay; a change another client makes at the same moment can still be lost, as the list is one document. `/whois <nick|@user:server>` asks the user's homeserver for their profile, so it works for anyone: it prints their nick and user ID with the profile's display name (`* Mod is @mod:example (Moderator Mo)`), the rooms you share (`* Mod shares rooms with you: @Ops Lobby`, with their rank in each) and their server (`* Mod's homeserver is example`); then, from their server's presence, whether they are away (with their away message) and how long they have been idle (`1hr 2mins`, as mIRC's `$duration`), unless they are active now. A server that does not share presence adds neither line. The answer prints in the window it was asked in, or in Status with `Options > Chat`'s `Show in active: Whois` off, as do its errors. The nick list takes several nicks, as mIRC's: Ctrl+click adds or removes one, Shift+click and Shift+arrows select a range. Its selection and scroll position stay while lines arrive and members come and go (a member who leaves drops out of it). Its right-click menu has `Whois`, `Devices`, `Verify`, `Direct Message`, `Mention/Insert Name` and a `Control` submenu (`Ignore`, `Unignore`, `Make Moderator`, `Remove Moderator`, `Allow to Speak`, `Revoke Speaking`, `Kick`, `Ban`); a right-click on a nick that is not selected selects only it, one on a selected nick keeps the selection. Each item acts on all the selected members it applies to, as mIRC's popups act on all selected nicks, and is greyed when it applies to none: it runs the typed command on each of them in list order (`Direct Message` opens direct messages with each, as `/query`); `Make Moderator`, `Remove Moderator`, `Allow to Speak` and `Revoke Speaking` are `/op`, `/deop`, `/voice` and `/devoice`: one change of the room's power levels for all of them, as `/op Bob Carol`, leaving out those it would not change; `Mention/Insert Name` inserts all their nicks (`Bob Carol `); `Verify` asks each of them, as `/verify Bob` then `/verify Carol`. A double-click on a nick opens direct messages with it, mIRC's default. A member who set no display name goes by the name part of their user ID (`ghost` for `@ghost:example`), in the nick list, the timeline, typing, reactions, completion and commands; a typed nick names the member the window shows by it, so `ghost` is refused as ambiguous while another member is named `Ghost`. The full ID shows where mIRC shows `user@host`: joins and parts, `/whois`, and after a nick another member also goes by (`ghost (@ghost:example)`). `~ & @ +` before a nick are ranks only. A user who is not a member shows by full ID.

Room Settings is mIRC's Channel Central for a room. `/channel` opens it for the active room and `/channel #room` for another joined room (direct messages have none); the treebar's room menu has `Room Settings...`, and a double-click in a room window's text, off a link and a quote line, opens it too, for that room even if another window comes to the front first, as mIRC's default double-click does; in direct messages it runs `/whois` on the other user, mIRC's default there, and in Status and threads it opens nothing. It opens greyed with `Reading the room's settings...` while it reads the room's current state from the server, then shows the room's `Name`, `Topic History` (the topic now, then the topics the window saw set, newest first; pick one or type a new one), the `Bans List` (each banned user, who banned them, when, and why) with `Remove`, and four settings: `Only moderators set the topic` is the topic's power level above the room's default, and checking it sets it to 50 (the moderator level, or one above the default if that is higher); `Moderated` is messages needing a level above the default, so only members given the level to speak (`/voice`) and moderators speak; `Invite only` is the `invite` join rule, unchecked `public`, and a room with another rule (knock, restricted) shows it half-checked, left alone unless changed; `Private (not in the Rooms List)` is the room not being published in the server's room directory. What you may not change is greyed, and the line above OK says so (`Some settings need a higher power level.` or `Only moderators can change these settings.`). OK sends only what changed, in one request: `Only moderators set the topic` and `Moderated` as one write of the room's power levels (read from the server first, so a rank change made meanwhile stays), then the join rule, the name, the topic, the directory listing, and each ban removed. The writes stop at the first the server refuses, whose error (`failed to set the join rule: ...`) prints in the room's window; the parts before it stay written. The room's window prints each change when the server's echo arrives (those two as `* Alice turns moderation on and lets only moderators set the topic`). Channel Central's `No external messages`, `Key`, `Limit`, the excepts and invites lists and its other settings have no Matrix counterpart and are not there. A room's name, join rule and encryption changes print as lines: `* Alice changes room name to 'Ops'` (`removes room name`) in the Topic colour, and `* Alice makes the room invite only` (`public`, `ask to join`, `open to members of its spaces`, `private`) and `* Alice turns on end-to-end encryption` in the Settings colour; a new room's window shows them for its creation too.

Away is Matrix presence. `/away <message>` (`Commands > Set Away...`) marks you away: your server is told you are `unavailable` with that message, and every sync says so too, so the next one does not undo it. `/away` alone or `/back` (`Commands > Set Back`, or a blank message in the Set Away prompt) marks you present again; the status bar says `away: <message>` or `back`. mIRC prints `* You have been marked as being away` and `* You are no longer marked as being away`; mirx prints them once the server has taken the change, then reads your presence back: if another of your sessions is active, the server still shows you online, and if it does not share presence (Synapse's `use_presence: false`), it shows you offline; either way a line says so. Away lasts for the session, across reconnects; a new session (after exiting or logging out) starts present. The server keeps the away message until it is replaced, so after a restart other users may still see your old message under `online` until you use `/away` or `/back` again.

Other users' presence comes with every sync. Members who are away (`unavailable`: their own `/away`, or Element's three idle minutes) or offline are drawn in the scheme's `Gray text` colour in the nick list, as HexChat greys away nicks; your own nick too, as your server sees you. Members whose server shares no presence (Synapse's `use_presence: false`, Conduit) are never grey. mIRC has no away colour; the order of the list does not change, and no line prints when someone goes away or comes back. Messaging an away user in direct messages (typed text, `/me`, a reply, `/msg`, `/query nick text`) prints `* Bob is away: lunch` in your direct messages window with Bob (after the message's echo), wherever you typed it, with `Options > Chat`'s `Show in active: Away` on; with it off, or with that window closed, the line prints in Status. mIRC prints it for every message; mirx prints it once per direct messages room for each away status, and again only after Bob comes back or changes his message, because Element marks users away after a few idle minutes and a line at every message would fill a normal conversation. An offline user gets no line (Matrix delivers to them anyway), nor do group rooms. The presence the store kept is shown again after a restart, before the server sends anything new.

The notify list is mIRC's buddy list, over the same presence. `/notify <nick|@user:server> [note]` adds a user (a nick names a member of a known room, as for `/ignore`; an ID anyone), or replaces the note of one already listed; `/notify -r <nick|@user:server>` removes them; `/notify` or `/notify -l` lists them, each with their note and, while connected, whether the server says they are on Matrix. The list is kept in `mirx.ini`'s `[notify]` section, as mIRC keeps it in `mirc.ini` (`n0=@bob:example.org lunch buddy`, `n1=...`), so it works signed out and survives Log Out. Once connected, Status says `* Bob is on Matrix` for every listed user the server says is on, and then, as they come and go, `* Bob is on Matrix` and `* Bob has left Matrix`, in the scheme's Notify colour (orange, as mIRC's). Away counts as on; only going offline is leaving. Each connect, reconnect included, calls the roll again, as mIRC does; nothing prints while disconnected, and a restart says who is on now, not who was when mirx last ran. Adding a user who is on prints the line at once. A Matrix server shares a user's presence only with users who share a room with them, and servers without presence (Synapse's `use_presence: false`, Conduit) share none: such users are never announced, and the listing shows no state for them. `/notify +<nick|@user:server> [note]` also performs a `/whois` on them each time Status says they came on, as mIRC's "Perform /whois" (`n0=+@bob:example.org`); every such user is asked about at once, so a roll call with many of them sends that many profile requests. With "Show notifies in active window" on (`[notify]`'s `active=on`, off by default), the notify lines also print in the active window. mIRC's notify window (`/notify -s`, the toolbar's Notify button) and per-network entries are not there yet; mIRC's bare `/notify` asks the server again, which on Matrix has nothing to ask, so mirx lists instead.

Nick colours are mIRC's: an ordered list of entries, each naming whom it colours and in which colour, that paints a nick in the nick list and where a line in a room or direct messages window names its sender (`<Bob>`, `* Bob waves`, an image's or file's line); the first entry that fits wins. An entry names a user (a nick, as `/notify` takes it, or a user ID) or a pattern over user IDs with `*` and `?` (`*` is anyone, `*:example.org` a server's users, `*bot*`), and may also ask for ranks in the window's room (some of `~&@+`, Any rank (any rank above member) or No rank) and that the user be on the notify list. The colour is one of the 16 palette colours, or auto, a colour picked from the user's ID (the same in every window and run) among the palette colours readable on the scheme's background. Away members stay grey in the nick list. `/cnick <nick|@user:server|pattern> <0-15|*> [ranks]` adds an entry, or updates the first one with the same nick or pattern; `-f` always adds a new one, `-a` is Any rank, `-n` No rank and `-y` the notify list (`/cnick -a * 4` colours every member with a rank red). `/cnick -r <nick|@user:server|pattern|N>` removes the first such entry, or the Nth as `/cnick` numbers them; `/cnick` lists them; `/cnick on` and `/cnick off` turn them all on and off. The list is kept in `mirx.ini`'s `[nickcolors]` section (`active=on`, `n0=* 4 any`, `n1=@bob:example.org auto ranks=@ notify`). Colours are only drawn: logs, copied text and the automation's line text carry none. mIRC's `-iopv` lists, idle time, message colours (`-m`), `$cnick` and `/cline` are not there.

`Tools > Address Book...` (`Alt+B`), the toolbar's Address Book button or `/abook` opens mIRC's Address Book at its Notify tab, `/abook -c` at its Control tab and `/abook -l` at its Colors tab; mIRC's other tabs (Info) and `/abook`'s other switches and nickname are not there. Notify lists the notify list, a `+` before the users who get a `/whois`, with their notes: `Add...` asks for a nickname (as `/notify` takes it), a note and `Perform /whois`; `Edit...` (or a double-click) changes an entry's note and `/whois`; `Delete` removes the selected one; and "Show notifies in active window" is the option above. Control lists the ignore list, as the server last sent it: `Add...` asks for a nickname (as `/ignore` takes it) and `Delete` removes the selected user; it is greyed until connected. Colors lists the nick colours in order, each nick painted in its colour, with their Apply conditions: `Add...` and `Edit...` (or a double-click) ask for whom (a nick, a user ID or a pattern), a colour (Auto or a palette colour), ranks, Any rank, No rank and On notify list, refused as `/cnick` refuses them; `Delete` removes the selected entry, `Up` and `Down` move it (the first that fits wins); and "Enable nick colors" is `/cnick on|off`. A refused nickname shows why in a message box. OK saves the notify list and the nick colours to `mirx.ini` at once, printing nothing, and sends the server one ignore or unignore per change, whose lines print when its echo arrives; Cancel or `Esc` changes nothing.

`/amsg <text>` and `/ame <action>` send a message or an action to every joined room (not direct messages), as mIRC's do to every channel; each room's window shows it as it is sent. `/describe <room|nick> <action>` sends an action to one room or user, and echoes `-> target * action` in the active window. `/clearall [-snq]` clears windows: `-s` the Status window, `-n` room windows and `-q` direct messages windows, combinable (`-nq`); without switches it clears them all, invite windows too. mIRC's other switches name windows mirx does not have. The menu labels `Set Away...` and `Set Back`, and `/describe`'s echo, follow mIRC's help and were not checked against a running mIRC.

`/echo [colour] [-ast] [#room] <text>` prints a line only you see, as mIRC's does: in the active window, Status with `-s`, another open window named by a `#alias` or `!id` first word (without `-a` or `-s`); `-t` gives it a timestamp, and the colour is a palette index 0 to 15. The text is printed as given: neither Markdown nor control codes format it. Another window's switchbar button turns maroon. `/say <text>` sends text to the active window as typed, so `/say /not a command` sends a line that starts with `/`; `/plain <text>` sends it without reading it as Markdown, as Element's `/plain` does. `//line` is mIRC's evaluated line: its identifiers (below) are evaluated, then it runs as a command, so `//echo -a my nick is $me` prints your nick in this room. Typing notifications are not sent for it.

Aliases are mIRC's, without the scripting language. `aliases.ini` in `%LOCALAPPDATA%\mirx\ui-shell` holds them in mIRC's format (`[aliases]`, then `n0=/j /join #$$1`, ...), and starts with mIRC's default aliases that mirx can run: `/dop /deop $$1`, `/j /join #$$1`, `/p /part #`, `/n /names #$$1`, `/w /whois $$1`, `/k /kick $$1 $2-`, `/q /query $$1` and `/s /server $$1`. An alias is a name and commands: `/name command | command`, or a block over several lines, `/name {`, a command per line, `}`. `$1`, `$2-` (the second parameter on), `$0` (how many), `#` (the window's room alias or ID, empty outside a room), `$chan` and `$me` (your nick there) are evaluated, `#$1` is the first parameter as a room, with `#` before it unless it starts with `#` or `!`, `$+` joins its neighbours, and a `$$` identifier left empty stops the whole alias silently. Any other `$name` is refused. Each command runs as if typed in the window active at the time; one that fails stops the alias, its error saying `(in alias /name)`. Each command runs once the server has answered the one before, so `/join #x | msg #x hi` greets in the room just joined, and `/q $$1 | say hi` greets in the direct messages `/q` opens; a server's refusal prints and the alias goes on. Meanwhile mirx stays usable, and a line typed or another alias runs at once. A command from a menu, a prompt or a dialog acts, and prints, in the window it was opened from, even if another window became active meanwhile (a join landing while a `Commands` prompt is open activates the joined room's window); the nick list's items in the window of that nick list. An alias overrides the built-in command of its name, which `/!name` still reaches, and an alias never calls itself, nor one already running it: it reaches the built-in. `/alias` lists the aliases, `/alias name command` adds or replaces one (blocks only in the file), and `/alias name` removes it; the file is saved at once. `Tools > Aliases...` (`Alt+A`) edits the whole file, in the text font, as mIRC's Scripts Editor does; OK checks it and selects the first wrong line, Cancel or `Esc` changes nothing. mirx's default alias list, and `/echo`'s and `/say`'s exact behaviour, follow mIRC's help where it could be read and were not checked against a running mIRC.

Typing in a room or thread window tells the room you are typing, as Element shows (`m.typing`), while the editbox holds a message that `Enter` would send (text, `/say text` or `/me action`, not another command); it stops when the editbox is cleared, by sending or by deleting the text. `Options > Chat > Messages`'s `Send typing notifications` turns it off (`[typing] send=`, on by default). Nothing is sent while not connected, or in a room you have not joined.

Sessions and verification. `Tools > Sessions...` opens the Sessions dialog: your sessions in a list (Session, Name, Verified, Last seen, which for this session reads `this session`), this session first, with a line under it counting them and saying when this session is not verified. Verify... (for a session that is not verified) closes the dialog and runs `/verify` for that session, or, on this session, asks your other sessions as `Tools > Verify This Session` does, so the emoji and `Tools > Confirm SAS` are at hand. Rename... asks for the session's new name (an empty name is refused). Sign Out... (any session but this one) asks as `/devices delete` does. Refresh reads the list again, and so does every rename and sign-out the server made, which still print their lines in the active window; the selected session stays selected. While the dialog is open, your list and the errors of its read, renames and sign-outs show only in it. `/devices [nick|@user:server]` (`Devices` in the nick list menu for a member's) lists a user's sessions in the active window, as `/whois` answers: one line per session with its device ID, its name in quotes, whether it is verified, and for yours when the server last saw it and which one is this session. `/devices delete <session>` signs out another of your sessions, after a Sign Out Session dialog whose default button is Cancel: a password account confirms with its password, typed in the dialog only; an account that signs in through the browser (OAuth 2.0) signs the session out on its account page, which mirx opens, and mirx is not told when that is done, so `/devices` shows it afterwards. This session is refused (File > Log Out signs it out), and so is an ID your account does not have. `/devices rename <session> <name>` renames one of your sessions, this one too. A user named `delete` or `rename` must be given by full ID. Another user's list opens with their identity's trust: verified, not verified, changed since you verified them, or no cross-signing (then verify one of their sessions). Trust is the crypto store's after asking their server afresh; mirx never shows a session as verified on any other say. `/verify` (`Tools > Verify This Session`) asks your other verified sessions to verify this one; `/verify <nick|@user:server>` (`Verify` in the nick list menu) asks a user to verify their identity with you, in your direct room with them, which is created if there is none; `/verify <nick|@user:server> <session>` asks that one session. The other side accepts, then both compare the emoji and confirm (`Tools > Confirm SAS`, `/verify confirm`); `/verify cancel` stops it. Several verifications can be under way at once, with different users (your own sessions count as one user: a second one with the same user would make the SDK cancel both, so mirx refuses to start it: `a verification with @bob:example is under way; answer or cancel it first: /verify cancel @bob:example`). Each one's Status lines, its emoji included, name its user and session: `* Verification with @bob:example (session B0B): compare the emoji or the numbers`, `* Verification requested by your session PH0NE`; one that starts while others are under way lists them (`* Also under way: @bob:example B0B (sas ready); ...`). `/verify accept`, `/verify cancel`, `/verify confirm` and `/verify reject`, and the Tools items, answer the verification under way when it is the only one; `/verify <action> <nick|@user:server> [session]` answers a given one. With more than one under way, an answer without a name is refused, never guessed, and the Tools items are greyed: `* /verify: 2 verifications are under way; name one: /verify confirm <user> [session]; under way: @bob:example B0B (sas ready), @carol:example C4R0L (requested)`, and every `Actions:` line names its verification (`/verify confirm @bob:example B0B`). A guess could confirm emoji you compared for another verification, and one that arrives while you type would move any "most recent" rule's target. An answer that does not apply, names no verification under way, or names a user with two, is refused with the list of those under way. A verification leaves the list when it is done or cancelled, by either side or by the SDK's 10-minute timeout, and Status says so; the status bar shows the latest (`verification: sas ready with @bob:example (session B0B) (+1 more)`). A user named `accept` must be given by full ID. The Status window's E2EE line says whether this session is verified; a session that needs it gets a red line saying how: `/verify` from another of your sessions, or `/e2ee recover` with your recovery key. The status bar notes an unverified session.

When another user's identity changes (they reset it, or someone took over their account), every encrypted room you share with them prints a red warning, as mIRC prints a nick change in every channel: `* Warning: Bob's identity was reset; /identity accept @bob:example to accept it, or /verify @bob:example`, or, if you had verified them, that your verification no longer holds. A background window's switchbar button lights up for it. The warnings come from the crypto store's own pinned and verified identities, watched in every joined encrypted room; mirx keeps no record of its own. `/identity accept <nick|@user:server>` (`Accept Identity` in the nick list menu, enabled only while a warning stands) accepts the new identity, or withdraws your verification of it; `/verify` verifies it again. `/devices nick` says when a user changed identity. A room's watch starts from its member list on the server, so when mirx starts offline, a change made while it was away shows only when that user's identity next changes.

`/e2ee reset` (`Tools > Reset E2EE Identity...`) is for when you have lost all your other sessions and your recovery key. It replaces your cryptographic identity with a new one that this session holds: it deletes your key backup and turns recovery off first, messages you cannot read now stay unreadable, and everyone who verified you sees your identity change. The dialog says so, and Cancel is its default button. A password session confirms with the account password, typed in the dialog only; an account that signs in through the browser (OAuth 2.0) approves the reset on a page mirx opens, and mirx waits up to 2 minutes for it, printing the page's address in Status; `/e2ee reset cancel` stops the wait. Status then says whether the reset happened, or was cancelled with your identity unchanged (the backup is gone either way), and that recovery is off until `/e2ee setup`.

A message mirx cannot decrypt shows as `* Bob sent an encrypted message that could not be decrypted`, in its thread or with its reply quote like any other. When mirx can tell why, a note in parentheses says so, and what to do if anything can be done: `(sent before you joined)`, `(sent before this session existed, and you have no key backup)`, `(sent before this session existed: /verify this session or /e2ee recover to read it)`, `(the sender shares keys only with verified sessions: /verify this session)` or `(the sender withheld its key)`. When this session is verified, or its key backup changes, the lines are read again: each decrypts, or its note says what is true now, so no line keeps asking you to verify a session you verified. A notice that the sender withheld a key, arriving after its message, shows only at the next such change. When its key arrives later (from another of your sessions, from the key backup after `/e2ee recover`, or from a key file) the line turns into the message in place, with any reactions and the latest edit it got meanwhile; a highlight lights up its window's switchbar button. `/e2ee export [file]` (`Tools > Export Room Keys...`) saves this session's room keys to a key file, encrypted with a passphrase, and `/e2ee import [file]` (`Tools > Import Room Keys...`) reads one, from mirx or another Matrix client, so its messages decrypt. The file is a full path; without one a Save or Open dialog asks for it. A dialog then asks for the passphrase (twice for an export); it is never typed on the command line, and OK stays greyed until it will do. Anyone with the file and its passphrase can read your encrypted messages. Status says when the file is written, or how many of its keys were new, or why it could not be read: a wrong passphrase, or a file that is not a key file.

Connecting works like mIRC's. With a saved session mirx restores it and starts syncing at startup, or, with connect on startup off, restores it and waits for `File > Connect` or `/server`; without one, Select Server opens. A restart shows the last session's rooms at once, before syncing and offline too: the treebar, the switchbar, every window with its topic and nick list (away users grey, as last seen), and the unread colours, from what mirx kept of the last sync; Status lists them (`* Synced rooms:`) before `Syncing with the homeserver`. With connect on startup off nothing is asked of the server until you connect, and the E2EE summary comes once connected. Status says each thing once: the room count once per sign-in or start (a later change, such as a join, shows in the treebar and the switchbar), and the E2EE summary once the server has answered and the session's encryption is set up, then again only when it changes or for `/e2ee`, followed by the commands that apply to it (`/e2ee refresh` while the server backup is not checked, `/e2ee setup` while recovery is off, `/e2ee recover` while it is incomplete). Every connect asks the server to answer at once rather than wait for news, so a quiet account is connected within moments. A sign-in, and a restore whose kept data is gone, sync once before showing the rooms, since there is nothing to show before. A server can take minutes to work out a big account's first sync, or the catching up after a long time away, so every sync waits up to 5 minutes for the answer beyond the time it lets the server wait for news; a dead connection is noticed sooner. If the sign-in's sync fails anyway, the session stands: Status says `Error during room list: initial Matrix sync failed: <reason>`, and the rooms come with the first sync that gets through. A failed request's reason says its cause, as in `error sending request for url (...): client error (Connect): tcp connect error: Connection refused`. Select Server takes a server name such as `matrix.org` (the client URL is discovered through `.well-known`), a homeserver URL, or nothing when the user is a full ID like `@alice:matrix.org`, then logs in and starts syncing. `/server [server]` and `File > Connect` reconnect a disconnected session, restore the saved one, or open Select Server; `/quit` and `File > Disconnect` stop syncing and keep the session, or cancel a sign-in or session restore still in progress, as mIRC's Disconnect cancels a connect; `File > Log Out` ends the session and removes its data from this computer: its messages, room keys and sync state. With recovery set up it first waits until the key backup holds every room key this session has, so a new session reads the same history after `/e2ee recover`. When no backup a new session could open would hold them all (recovery off, incomplete or not known yet, key backup off, or the upload failed), a `Log Out` dialog says so and what keeps them (`/e2ee setup`, `/e2ee recover`, `/e2ee export`); its default is Cancel, which leaves the session as it was, and its `Log Out` logs out all the same. While Log Out waits for the key backup and the server, Status says `Logging out; File > Disconnect stops it` and the status bar `logging out`; `File > Disconnect` or `/quit` stops it (`Log Out cancelled; still signed in`), keeping the session, disconnected. If the server's answer was already on its way, the server may have ended the session anyway: the next Connect then says it was signed out. When the server does not end the session, because it cannot be reached (the network or the server is down) or it answers with an error, the `Log Out` dialog says so, with the reason, and offers to remove the session from this computer only: its `Remove` deletes the saved login and the session's messages, room keys and sync state here without asking the server again, and Status says `Logged out on this computer only: <server> still lists this session (<device>) until you sign it out from another session (Tools > Sessions... there)`. The server keeps the session (its device) in the account's list until another session signs it out, in mirx's Sessions dialog or any other client's session list. Cancel, the default, keeps the session, syncing again if it was, to try again later. The room-key warning above still comes first. A session the server already ended logs out too, as usual. Every sign-in is a new session, and starts afresh. A request the server answers with an error such as 502 or 503 is retried for a few seconds, then fails with it. A request the server is slow to answer holds up only what has to wait for it: while older history loads, lines, joins and the rest go on, and exiting waits for nothing but the read receipts and the line marker (below). Exiting, by `File > Exit`, `/exit`, closing the window or Windows ending the session, makes the window disappear at once; the read receipts and the line marker mirx sent the server get up to 3 seconds more to reach it, and then the program ends whatever the server did, so `mirx-ui.exe` may stay in Task Manager that long. Nothing else is waited for: a request still under way is dropped, and what was queued behind it never goes.

A connection that drops is tried again, as in mIRC. With `Connect > Options`' `Reconnect on disconnection` on, a sync that was up and failed by itself (the network went away, the server stopped answering, or it answers only with errors, as a proxy in front of a stopped server does, after a few retries over about 8 seconds) logs `Disconnected: <reason>` and `Reconnecting to <server>` in Status and syncs again at once (without a `Syncing with the homeserver` line: `Reconnecting to` and `Connect retry` say it). With `Enable connect retry` on, a connect that fails, including that reconnect and a connect at startup with the network down, is retried after `Delay` seconds, up to `Retry` times: Status logs `Connect retry #1 <server>`, `#2`, and so on, and the status bar says `disconnected; retrying in 10 seconds` meanwhile. Once a sync succeeds Status says `Reconnected to <server>` and the count starts over; when the retries run out it says `Not retrying: 99 retries failed. File > Connect or /server tries again.` Both are on by default, with 99 retries 10 seconds apart; these defaults are mirx's. `File > Disconnect` and `/quit` cancel a pending retry, and `File > Connect` or `/server` tries at once. A session the server signed out (its access token no longer valid, and its refresh token, if it has one, refused too) is never retried: Status says so, `Disconnected: <server> signed this session out (<reason>). /e2ee export saves its room keys; File > Log Out ends it, then sign in again.`, and the way back is just that. Starting offline works: the saved session is restored with its rooms, without an error line, while the connect is retried; a line typed meanwhile shows `(waiting to send)` and goes once the server answers. Unlike mIRC, whose retry count and delay sit behind a `Retry...` button in their own dialog, mirx puts the `Retry` and `Delay` fields on the `Connect > Options` page, greyed while retry is off, so OK checks every field in one place.

Perform on connect is mIRC's. `Connect > Options`' `Perform...` button opens the `Perform` dialog: `Enable perform on connect`, and `Perform commands:`, one command line per line, as an alias's line (below): the `/` is optional, `|` separates commands, and identifiers are evaluated. Its OK checks the lines, as the Aliases dialog does (a wrong one is named and selected, and the dialog stays open), and hands them to the Options dialog, whose OK saves them; Options' Cancel drops them too. `mirx.ini` keeps them in `[perform]` (`enabled=on`, then `n0=join #rust:matrix.org`, `n1=msg @helpbot:example.org hello | echo -s done`, ...). Each time mirx connects, the first connect, `File > Connect`, `/server` and every reconnect and retry that connects, the lines run in order, once Status has said the connect, as if typed in Status: `#` is empty, `$me` is your user ID, a `$$` identifier left empty stops its line silently, and text that is not a command goes nowhere (`say hi` is refused: there is no room in Status). A command that fails prints its error in Status ending ` (in perform)`, and stops its line; the next line still runs, so one stale `/join` does not skip the `/msg` after it. Each command, and each line, runs once the server has answered the one before, as an alias's do, so `join #rust:matrix.org` then `msg #rust:matrix.org hi` greets on the first connect. Commands that open windows (`/join`, `/query`) open and activate them, as in mIRC, and one that opens a dialog (`/channel`, `/abook`) opens it; the remaining lines run once it closes. Answers that come later (a `/whois`, a server's refusal) print in the window in front when they arrive. mIRC keeps a list per network; mirx has one account, so one list, and no `Network` drop-down. A `/server` line reconnects on every connect, as in mIRC.

A message typed while the connection is down shows in grey, ending ` (waiting to send)`, and goes out by itself, once and in order, as soon as the server answers again; it then reads as any sent message. A message that ends ` (failed)` and stays red was refused by the server (for example, no permission to post there) and is not sent again.

Leave Password empty in Select Server to sign in with your browser, for servers and accounts without a password: those of the Matrix Authentication Service (matrix.org among them), SSO-only servers, and accounts made with "Continue with Google" and the like. User may stay empty, or hold a full user ID such as `@alice:matrix.org` to pre-fill the server's page. mirx opens the server's sign-in page in your default browser and prints its address in Status, in case no browser opened. Once you have signed in there, the page sends the browser back to mirx, which signs in and starts syncing; the page then says whether it worked. A server with OAuth 2.0 (the Matrix Authentication Service) is used through it; otherwise its single sign-on is used, and a server with neither says so and asks for a password. While mirx waits, `File > Disconnect` or `/quit` cancels the sign-in. The device name names the new session for password and single sign-on; an OAuth 2.0 server names it after the client, mirx, and shows the project's homepage on its consent page. mirx listens for the browser's return on `127.0.0.1` only, on a fresh port at an unguessable address, and only until that one sign-in ends.

`/font [-b] <size> <font name>` (or `/font` and every window's system-menu `Font...` for the font dialog) sets the one text font used by every window's text area, nick list and editbox; mIRC's default is Fixedsys 9. `/timestamp [on|off|-f format]` shows, toggles or formats line timestamps, which are in local time; the format takes mIRC `$asctime` tokens (`HH H hh h nn n ss s tt TT dd d mm m yy yyyy`, everything else literal). A missing file means the defaults; a file mirx cannot parse stops startup with an error naming the line, rather than being overwritten. The Wine test scripts pin `TZ=UTC` so timestamps are deterministic.

Logging works like mIRC's. `/log on` starts logging the active window to a file, `/log off` stops it, and `/log` says whether it is on; `/log on|off #room` acts on another room's open window. Every window with an editbox has `Logging` on its window menu, checked while the window logs. Status and room windows have logs; a thread window's `Logging` and `/log` are its room's. `Options > Chat > Logging` turns on logging automatically for rooms, direct messages or both, from when their window first shows them joined (an invite starts once it is joined). Windows already open keep the log they have. Logs go to `%LOCALAPPDATA%\mirx\ui-shell\logs`, one file per window: `status.log`, a room's alias or ID, and for direct messages the other user's ID, with `:` as `.` (`#rust.matrix.org.log`, `@bob.example.org.log`). Each session is appended in CRLF lines, between `Session Start:` and `Session Ident:` lines (`Session Ident: Rust (#rust:matrix.org)`) and a `Session Close:` line, with a blank line before the next session. Lines are written as the window shows them, with the timestamp format of `Chat > Messages` unless `Timestamp logs` is off, as plain text: formatting is not written. A log writes the lines that arrive while it is on, once each, as they show; what decides is when a line arrived, not the time the server gave it. History scrolled back to is never written. A log turned on with `/log on` or the menu starts with the next line. An automatic log also writes what arrived since the room's window last closed, so the message that reopens a closed direct messages window is in its log, and so are messages received while mirx was closed (on the first sign-in with a new profile, that is the few recent messages per room the server sends with the first sync). A message is written once it is sent. Edits and deletions do not change a line already written, nor does a message decrypting late: its log keeps the line that it could not be decrypted. Closing the window, leaving the room, `/log off` and exiting close the log. A write that fails stops the log and says why in the window.

Tray and tips work like mIRC's. With `Options > Display > Tray`'s `Place mirx in tray when minimized` on, minimizing mirx hides it behind an icon in the notification area; with it off, holding `Shift` while minimizing does the same. `Always show mirx icon in tray` keeps the icon there while mirx is on screen too, and `On startup minimize mirx to tray` starts mirx hidden in it. Double-clicking the icon (or clicking it, with `Single click on tray icon to open` on) brings mirx back, or minimizes it while it is the active application. Right-clicking the icon lists the windows in switchbar order, those with new messages checked; choosing one brings mirx back with that window active. `Options > Display > Tips` shows a tip while mirx is not the active application, for highlights and direct messages by default and for every room message if chosen; a muted room never shows one, and a `Mentions and keywords` room only for highlights. Unlike mIRC's own tip windows, a tip is a Windows notification from mirx's tray icon (shown just for it if the icon is not already there), so Windows keeps the queue and decides how long each shows, and Focus Assist applies; there is no queue size or display time to set. Clicking a tip brings mirx back with the tip's window active. The icon is mirx's own; mIRC's icon animation and `/tray` are not there.

Like mIRC, a character the text font has no glyph for draws in the first fallback font that has one, at the text font's height and on its baseline, in every text area and nick list: Segoe UI, Tahoma, Segoe UI Symbol, Segoe UI Emoji, Noto Emoji, then the Windows script fonts (Nirmala UI, Microsoft YaHei, Yu Gothic, Malgun Gothic and others), whichever are installed. Emoji are monochrome; sequences (ZWJ families, skin tones, flags) draw as their component glyphs, and invisible format characters such as variation selectors are not drawn. The Wine test prefixes get the monochrome Noto Emoji font from the devshell (`MIRX_WINE_FONTS`), so the harness chain is Fixedsys, Tahoma, Noto Emoji.

Replies and edits read like mIRC lines with a dim note. A reply has a grey quote line directly above it, `    > <Alice> are we deploying today? the build looks gr...`: the replied-to line without its timestamp, first line only, cut to 60 characters; a message that is not loaded is fetched from the server with its latest edit, and follows later edits and its deletion as a loaded one does; a redacted one reads `message redacted`. A thread message replying to its own thread's root has no quote. Double-click a quote line, or choose the message menu's `Go to Original Message`, to scroll to the message it quotes and select it; older history is loaded until it is found (the status bar says `finding the original message...`), and a quote in a thread window of a message outside the thread opens the room window. Scrolling the window meanwhile gives up. Plain-text reply fallbacks (`> <@alice:example.org> ...`) that older clients send are stripped. An edited message ends with ` (edited)` and shows its latest edit, whatever order the edits came in, and also when scrolling back through history (the server sends a message's latest edit with it). Deleting an edit shows what it replaced, as Element does: the latest edit left, or the message's own text without ` (edited)`; deleting an older edit changes nothing shown. A message scrolled back through history comes with the edits mirx saw of it (live, or on newer pages) and the server's latest, so deleting the latest shows the edit before it if mirx saw that one, and otherwise the message's own text. Edits by anyone but the message's sender are ignored, as Element does. The message right-click menu's `Reply to Message` and `Edit Message`, or `/reply <event-id>` and `/edit <event-id>` without text, arm the window's editbox: a navy line under the timeline says `* Replying to <Alice> ... (Esc cancels)`, and the next line typed there (plain, `/say /text` or `/me`) is sent as the reply or the new text, while other commands leave it armed. Edit puts the message in the editbox as one would type it (`/me waves` for an emote): a formatted message's own `body`, its Markdown as typed in mirx or Element (a rich-text editor's plain `body` otherwise, which is what Element edits too), else the text shown. It is offered only for your own text and emotes. `Esc` disarms the editbox; for an edit it also clears the old text. `/reply <event-id> <text>` and `/edit <event-id> <text>` still send at once. A reply also mentions the sender of the message it answers. `Up` in the editbox stays mIRC's per-window history; it does not edit the last message.

Naming someone notifies them. Every message mirx sends lists whom it mentions (`m.mentions`), which is what servers notify by since Matrix 1.17 dropped matching names in the text: each member whose nick (display name, or the name part of their ID) it contains as a whole word, ignoring case, or whose full user ID it contains, and the whole room for `@room` (if your power level lets you notify it). Where names overlap the longest wins, so `Bob Smith` names Bob Smith and not Bob. The name is sent as a pill, a link to the user that other clients show as a chip, unless several members share it: then all of them are mentioned and none is pilled. Tab completion and the nick list's `Mention/Insert Name` insert exactly such a name. The text sent is what was typed; an edit notifies only the members it newly names. The members mirx knows are those of rooms whose window was opened, so `/msg` to a room never opened may miss a name.

Formatting is typed as Markdown, as in Element: `**bold**`, `*italic*` or `_italic_`, `~~strikethrough~~`, `` `code` ``, `[label](https://...)` and `<https://...>` links, and on a line of its own `> quote`, `# heading` or `1. item`. With text selected, `Ctrl+B` wraps it in `**`, `Ctrl+I` in `*` and `Ctrl+E` in `~~`, and it stays selected; with none, the pair is typed and the caret goes between. Markdown has no underline or colour, so `Ctrl+U`, `Ctrl+K`, `Ctrl+R` and `Ctrl+O` do nothing. HTML typed in the editbox is sent as text. A line is sent with the text as typed as its `body` and, when the Markdown formats something or a nick becomes a pill, the HTML it renders as `formatted_body`; a line with neither is plain text. A nick in code or in a link's text is not linked, but the message still mentions them. As in Element, runs of spaces collapse in the HTML. `/plain <text>` sends the text as it is. Received HTML is shown with its styles: bold, italic, underline, strikethrough and colours (`data-mx-color`, `data-mx-bg-color`, `<font color>`), headings bold, lists as `* item` or `1. item` lines, quotes as `> ` lines, code blocks as they are, links as `label (https://...)`, images by their alt text, spoilers black on black. As in a browser, runs of spaces in received formatted text collapse to one. Not supported yet: formatted room topics. Control codes received in plain text are not interpreted. Under Wine the Fixedsys text font has no italic (Wine does not slant raster fonts), so italic shows only in the fallback fonts; Windows draws it slanted.

The line marker is mIRC's: a rule across a room window below the last line read there, so what arrived since starts below it. It sits below that line and its reactions, above the next message, and only while there is a next message. Its place is the room's read marker on the server (`m.fully_read`), the one Element shows as its "new messages" line, so mirx and other clients agree on it. A marker on something the window shows no line for (a reaction, an edit, a hidden event) sits below the last line before it. Activating a room window sends a read receipt only, which clears its unread colour without moving the marker. The marker moves when you leave the window, by activating another one, by closing or minimizing it, or by minimizing mirx (to the taskbar or the tray): if the rule was on screen while the window was active (or the window had no rule), the marker goes to the window's last line; a window left without its rule ever shown keeps it where it was, so unread lines scrolled past are not lost. Restoring mirx enters its active window again. Exiting leaves the active window too, so its marker moves as when you leave it, and the next start and your other clients see it there. The marker moves only while connected. `Ctrl+L` scrolls the active room window back to its line marker, putting the rule at the top, and loads older history until it reaches the marker (`finding the line marker...`); it says `* this window has no line marker` elsewhere. `Options > Display`'s `Show line marker` hides the rule, and `Line marker` sets its colour, red by default (`[marker] show=` and `color=`, a palette index; mIRC's help names no default, its users call the marker "the red line", and this was not checked against a running mIRC); hiding it does not stop the marker moving, and `Ctrl+L` then scrolls to the marked line. Thread windows have no line marker: Matrix keeps one read marker per room. The rule is never copied, saved with the buffer or logged.

Reactions show on a dim line under the message that names who reacted, as mIRC lists nicks: `    reactions: 👍 Alice, Bob  heart Carol, Dave, Erin and 2 more`. Each reaction names its first three reactors by nick (a user who is not a member shows by user ID), then counts the rest; reactions keep the order they were first given in, and a long line wraps. A message loaded later, by scrolling back or when a window opens, shows the reactions mirx saw of it while it was not loaded, live or on newer pages (servers send no reactions with a message). A reaction disappears when it is taken back (`/unreact`, or from another client) or removed by a moderator, however it arrived.

Every room window's window menu has `Send File...`, which opens the standard Open dialog (`Send File to <room>`) and uploads the chosen file to that room, as mIRC's DCC Send dialog does; `/sendfile` without a path opens the same dialog for the active room, and `/sendfile <path>` sends at once. Threads cannot take files yet. A file's type comes from its extension, so pictures, videos and audio arrive as such (`.png` as an image, `.mp4` as a video, `.mp3` as audio); anything else, including `.svg`, is sent as a plain file.

Find is UI-scoped. Status and Thread Find search only loaded text, while Room Find searches loaded text first and can page older room history through backfill. `/find <text>`, every window's system-menu `Find Text...`, and `Ctrl+F` all invoke the same behavior; Find does not use Matrix server-side search.

## Mouse and keys

Long lines wrap at spaces and commas, and wrapped lines are indented by two characters, as in mIRC; a word longer than a line is split. A window lays out again only the lines that changed: a new message wraps one line, and a resize rewraps only the window resized. Message windows scroll as in mIRC. The mouse wheel scrolls the window; Wine sends the wheel to the focused window, so the editbox passes it on to its window's text. In the editbox, `Page Up` and `Page Down` scroll a page, `Ctrl+Page Up` and `Ctrl+Page Down` a line, and `Ctrl+Home` and `Ctrl+End` to the top or the end while the editbox is empty (with text in it they move the caret). Reaching the top of a room window, by wheel, key or scroll bar, loads older history, one request per gesture. A window at its end stays at its end as lines arrive and when it is resized.

Each window keeps at most `Options > Other`'s `Window buffer` lines, 5000 by default (100 to 50000), as in mIRC: at its end, a window drops its oldest lines as new ones arrive, after they were shown and logged. A window scrolled back keeps every line until it returns to its end, and lowering the setting shortens the windows at their end at once. A room window's messages and its own lines count; a message's quote and reaction lines go with it. Unlike mIRC, a room window's dropped messages are not gone: scrolling to its top loads them back from the server, from the oldest line it kept. A room window keeps a message still sending and every line of a thread whose window is open, and the lines below them, so it may stay over the buffer while one is. Every window with an editbox has `Buffer` on its window menu: `Clear` empties the window, as `/clear` does (a thread window has nothing of its own to clear), and `Save...` saves its lines to a text file, by default in the logs folder under the window's log name. `/savebuf <file>` saves the active window's lines without the dialog, a relative file in the logs folder; `/savebuf` alone opens the dialog. A saved buffer has the lines as the window shows them, without colour or style codes, and without the lines about the window's state (who is typing, older history loading, what the editbox replies to).

The window keys are mIRC's. `Alt+1` to `Alt+9` activate the first nine switchbar buttons. `Ctrl+Tab` and `Ctrl+Shift+Tab` step to the next or previous window in switchbar order, wrapping round. `Ctrl+N` steps through rooms only (not direct messages), and `Ctrl+Q` through direct messages only. `Alt+X` maximizes or restores the active window. `Ctrl+T` moves the focus into the treebar and back to the active window. In the treebar the arrow keys move between items and activate the windows they reach, and the focus stays in the treebar. `Left` goes to an item's folder and then collapses it; `Right` expands it. MDI's own `Ctrl+F6` still steps through windows in the order they were last active. `Ctrl+L` scrolls back to the line marker.

Dragging over text marks it in inverse video, and releasing the button copies it to the clipboard, as mIRC does. The copy is the text as received, with its timestamp and nick: a message wrapped over several lines is one line, and lines are separated by CRLF. The copy is plain text, without formatting. A click without a drag copies nothing.

Links are mIRC's hotlinks: the pointer becomes a hand over them, and a double-click opens them. Web addresses (`https://`, `http://`, `ftp://`, `www.`) open in the default browser. Matrix links open in mirx: a `matrix.to` permalink, a `matrix:` URI, or a bare `#alias:server` or `!id:server`. A room you are in becomes the active window, any other room is joined through the link's servers, a link to a message opens its room, and a link to a user opens direct messages with them. Nicks are hotlinks too, as in mIRC: the sender's nick on a message or action line, and a pill (a name the sender linked to its user), open direct messages with that user on a double-click. A double-click elsewhere in a room window opens Room Settings, and in direct messages runs `/whois` on the other user. Punctuation that ends a sentence, and a closing bracket the link did not open, are not part of a link; `C#` and `issue#12` are not links. `/join` of a room you are already in activates its window too.
